# 1.1 SQL 파싱과 최적화
> 처음부터 정확히 내용을 이해하려고 하기 보다는 한 번 쭉 읽고 정리해본다.
- SQL은 선언이고, DB는 옵티마이저를 통해 실행 방법을 결정하며, 그 결과가 실행계획이다.
---
## 1.1.1 구조적, 집합적, 선언적 질의 언어
### 실습 맥락
- 사원(EMP) 테이블과 부서(DEPT) 테이블을 조인한 뒤 - 사원명 순으로 정렬하는 로직 구현 
    - 절차적 언어 Java
        ``` java
        for (Dept d : deptList) {
            for (Emp e : empList) {
                if (e.getDeptNo() == d.getDeptNo()) {
                    result.add(e, d);
                }
            }
        }
        result.sortByName();
        ```
        - 실제 데이터 접근 경로, 루프 순서, 조인 방식, 정렬 방식과 같은 실행 절차를 직접 지정한다.
    - 구조적 질의 언어 SQL
        ``` sql
        SELECT E.ENAME, D.DNAME
        FROM EMP E
        JOIN DEPT D ON E.DEPTNO = D.DEPTNO
        ORDER BY E.ENAME;
        ```
        - 이 SQL에서 **조인 순서, 조인 방식, 정렬 방법**은 개발자가 지정하지 않는다.
        - 개발자는 결과를 선언하고, DB는 옵티마이저를 통해 실행 절차를 만들어낸다.
### SQL(Structured Query Lanaguage)
SQL은 다음과 같은 특성을 가진다.
- **구조적(Structured)**
    - SELECT, FROM, WHERE 등 고정된 문법 구조를 가진다.
- **집합적(Set-based)**
    - 한 건씩 처리하지 않고 결과 집합 전체를 대상으로 연산한다.
- **선언적(Declarative)**
    - *무엇*을 가져올지는 기술하지만 *어떻게* 가져올지는 기술하지 않는다.

> SQL은 실행 절차를 포함하지 않는다.
>    - 개발자는 SQL을 통해 필요한 결과 집합의 조건만 선언한다. 
>    - 결과를 얻는 실행 절차(조인 순서, 조인 방식, 정렬 방법)는 명시하지 않는다. 
>    - 결과를 얻기 위한 접근 경로와 실행 절차는 DB에 위임된다. 

> 절차적 프로그래밍 기능을 구현할 수 있는 확장 언어도 존재한다. 
> - 오라클 PL/SQL, SQL Server T-SQL

> 실제 실행을 위한 절차적 로직을 생성하고 선택하는 역할을 수행하는 것이 
**SQL 옵티마이저**다.

## 1.1.2 SQL 최적화
- DBMS 내부에서 프로시저를 작성하고 컴파일해서 실행 가능한 상태로 만드는 만드는 전 과정을 `SQL 최적화`라고 한다.
> 사용자는 필요한 결과를 SQL로 선언한다

> 옵티마이저는 해당 SQL에 대한 실행계획을 결정한다

> DB 실행 엔진은 이 실행계획을 기반으로 데이터를 처리한다
### 1.1.2.1 SQL 파싱
- 사용자가 입력한 SQL을 전달받으면 SQL Parser가 파싱을 진행한다.
    * SQL Parser (SQL 텍스트를 `DB가 이해하는 구조`로 변환하는 해석기)
        - DB가 SQL을 받았을 때, 이 문장이 규칙(문법, 의미)에 맞는지 검사하고, 내부 처리가 가능한 형태로 구조화된 트리로 바꾸는 모듈            
        - Syntax 체크 : 문법적 오류 확인 (사용할 수 없는 키워드, 누락된 키워드, 순서)
        - Semantic 체크 : 의미상 오류 확인 (존재하지 않는 테이블 또는 컬럼, 오브젝트에 대한 권한)
        - 파싱 트리 생성 : SQL문을 이루는 개별 구성요소를 분석해서 파싱 트리를 생성
### 1.1.2.2 SQL 최적화
- SQL 옵티마이저는 미리 수집한 시스템 및 오브젝트 통계정보를 바탕으로 다양한 실행경로를 생성해서 비교한 후 가장 효율적인 하나를 선택한다.
### 1.1.2.3 로우 소스 생성
- 로우 소스 생성기(Row-Source Generator)를 통해 SQL 옵티마이저가 선택한 실행경로를 실제 실행 가능한 코드 또는 프로시저 형태로 포맷팅하는 단계
## 1.1.3 SQL 옵티마이저
- 사용자가 원하는 작업을 가장 효율적으로 수행할 수 있는 최적의 데이터 액세스 경로를 선택해 주는 DBMS의 핵심 엔진
### 1.1.3.1 옵티마이저의 최적화 단계
1. 사용자로부터 전달받은 쿼리를 수행하는 데 후보군이 될만한 실행계획들을 찾아낸다.
2. 데이터 딕셔너리에 미리 수집해 둔 오브젝트 통계 및 시스템 통계정보를 이용해 각 실행계획의 예상비용을 산정한다.
3. 최저 비용을 나타내는 실행계획을 선택한다.
## 1.1.4 실행계획과 비용
- DBMS에도 `SQL 실행경로 미리보기` 기능인 실행계획(Execution Plan)이 있다.
    - SQL 옵티마이저가 생성한 처리절차를 사용자가 확인할 수 있게 트리 구조로 표현한 것
    - SQL이 테이블을 스캔하는지 인덱스를 스캔하는지 확인할 수 있다.
    - SQL이 인덱스를 스캔한다면 어떤 인덱스인지를 확인할 수 있고, 예상과 다른 방식으로 처리된다면 실행경로를 변경할 수 있다.
    - SQL Plus에서 AutoTrace를 활성화하고 SQL을 실행하면 실행계획을 확인할 수 있다.
- 비용(Cost)
    - 쿼리를 수행하는 동안 발생할 것으로 예상하는 I/O 횟수 또는 예상 소요시간을 표현한 값
    - Table Full Scan을 하도록 full 힌트를 지정했을 때보다 특정 인덱스를 선택했을 때가 비용이 적으면 SQL 옵티마이저가 비용이 적은 실행계획을 선택할 것이다.
    - 실측치가 아닌 예상치이기 때문에 실제 수행할 때 발생하는 I/O 또는 시간과 많은 차이가 난다.
## 1.1.5 옵티마이저 힌트
- 티맵과 네이버 지도를 동시에 사용할 때, 서로 다른 길로 안내하는 것처럼 SQL 옵티마이저도 대부분 좋은 선택을 하지만, 완벽하진 않다.
- SQL이 복잡할수록 실수할 가능성도 크다.
- 운전자 자신만 아는 정보나 경험을 활용해 더 빨리 목적지에 도착할 수 있는 것처럼 통계정보에 담을 수 없는 데이터 또는 업무 특성을 활용해 개발자가 직접 더 효율적인 액세스 경로를 찾아낼 수도 있다.
    - 이 때 옵티마이저 힌트를 이용해 데이터 액세스 경로를 바꿀 수 있다.
        ```SQL
            SELECT /*+ INDEX(A 고객_PK) */
                고객명, 연락처, 주소, 가입일시
            FROM 고객 A
            WHERE 고객ID = '000000008'
        ```
        - `--` 는 줄바꿈 오류가 발생할 수 있기 때문에 `/* */`를 권장한다.
        - 힌트 안에 인자를 나열할 때 `,` 콤마를 사용할 수 있지만 힌트와 힌드 사이에 사용하면 안된다.
            ```SQL
                /*+ INDEX(A A_X01) INDEX(B, B_X03) */ 모두 유효
                /*+ INDEX(C), FULL(D) */ 첫 번째 힌트만 유효
            ```
        - 테이블을 지정할 때 스키마명까지 명시하면 안 된다.
            ```SQL
                SELECT /*+ FULL(SCOTT.EMP) */ 무효
            ```
        - FROM 절 테이블명 옆에 ALIAS를 지정했으면 힌트에도 반드시 ALIAS를 사용해야 한다.
            ```SQL
                SELECT /*+ FULL(EMP) */ 무효
                FROM EMP E
            ```
- 어플리케이션 환경에 따라 옵티마이저의 작은 실수가 기업에 큰 손실을 끼치는 중대한 시스템이라면 옵티마이저의 자율적 판단에 맡길 수 없어서 힌트를 빈틈없이 기술해야 한다.
- 자주 사용하는 힌트 목록
    - 액세스 방식
        - FULL : Table Full Scan으로 유도
        - INDEX : Index Scan으로 유도
        - INDEX_DESC : Index를 역순으로 스캔하도록 유도
        - INDEX_FFS : Index Fast Full Scan으로 유도
        - INDEX_SS : Index Skip Scan으로 유도    
    - 조인방식
        - USE_NL : NL 조인으로 유도
        - USE_MERGE : 소트 머지 조인으로 유도
        - USE_HASH : 해시 조인으로 유도
        - NL_SJ : NL 세미조인으로 유도
        - MERGE_SJ : 소트 머지 세미조인으로 유도
        - HASH_SJ : 해시 세미조인으로 유도
    - 쿼리 변환
        - MERGE : 뷰 머징 유도
        - NO_MERGE : 뷰 머징 방지
        - UNNEST : 서브쿼리 Unnesting 유도
        - NO_UNNEST : 서브쿼리 Unnesting 방지
        - PUSH_PRED : 조인조건 Pushdown 유도
        - NO_PUSH_PRED : 조인조건 Pushdown 방지
        - USE_CONCAT : OR 또는 IN-List 조건을 OR-Expansion으로 유도
        - NO_EXPAND : OR 또는 IN-List 조건에 대한 OR-Expansion 방지
    - 기타
        - APPEND : Direct-Path Insert로 유도
        - DRIVING_SITE : DB Link Remote 쿼리에 대한 최적화 및 실행 주체 지정(Local 또는 Remote)
        - PUSH_SUBQ : 서브쿼리를 가급적 빨리 필터링하도록 유도
        - NO_PUSH_SUBQ : 서브쿼리를 가급적 늦게 필터링하도록 유도
