# 1.3 데이터 저장 구조 및 I/O 메커니즘
`I/O 튜닝이 곧 SQL 튜닝이다.`
## 1.3.1 SQL이 느린 이유
- SQL이 느린 이유는 디스크 I/O 때문이다.
    - I/O = 잠(SLEEP)
        - OS 또는 I/O 서브시스템이 I/O를 처리하는 동안 프로세스는 잠을 잔다.
    - 프로세스 = 실행 중인 프로그램
        - 생성 이후 종료 전까지 준비, 실행, 대기 상태를 반복
        - 디스크에서 데이터를 읽어야 할 땐 CPU를 OS에 반환하고 잠시 수면(waiting) 상태에서 I/O가 완료되기를 기다린다.
- I/O Call 속도는 Single Block I/O 기준 평균 10ms
    - 초당 100 블록을 읽는다.
    - 큰 캐시를 가진 SAN 스토리지는 4~8ms쯤 되어 초당 125~250 블록을 읽는다.
    - SSD까지 활용하는 스토리지는 1~2ms, 초당 500~1,000 블록을 읽는다.
    - SQL이 Singlo Block I/O 방식으로 10,000 블록을 읽으면 10초 이상 기다려야 한다.
        - I/O 튜닝이 안되어 있는 시스템이면 디스크 경합이 심해지는 만큼 대기 시간도 늘어난다.
## 1.3.2 데이터베이스 저장 구조
- 테이블을 저장하려면 테이블스페이스를 생성해야 한다.
    - 테이블스페이스 
        - 여러 개의 데이터 파일로 구성된 세그먼트를 담는 컨테이너
    - 데이터 파일 (물리적 구조)
        - OS 레벨에서 확인 가능한 디스크에 실제 존재하는 DB 데이터 저장 파일
            - .dbf 파일
        - 세그먼트에 할당된 모든 익스텐트가 같은 데이터파일에 위치하지 않을 수 있다.
            - 서로 다른 데이터 파일에 위치할 가능성이 더 높다.
            - 하나의 테이블 스페이스를 여러 데이터 파일로 구성하면, 파일 경합을 줄이기 위해 DBMS가 데이터를 가능한 한 여러 데이터 파일로 분산해서 저장한다.
    - 세그먼트 
        - 데이터 저장이 필요한 오브젝트
            - 테이블, 인덱스, 파티션, LOB 등
        - 테이블, 인덱스를 생성할 때 데이터를 어떤 테이블스페이스에 저장할지를 지정
        - 여러 익스텐트로 구성됨
        - 파티션 구조가 아니면 테이블, 인덱스도 하나의 세그먼트 
        - 테이블, 인덱스가 파티션 구조라면, 각 파티션이 하나의 세그먼트
        - LOB(BLOB, CLOB) 컬럼
            - 그 자체가 하나의 세그먼트를 구성
            - 자신이 속한 테이블과 다른 별도 공간에 값을 저장
    - 익스텐트
        - 공간을 확장하는 단위이자 연속된 블록들의 집합
        - 테이블이나 인덱스에 데이터를 입력하다가 공간이 부족해지면 해당 테이블스페이스로부터 익스텐트를 추가로 할당받는다.
        - 여러 개의 데이터 블록으로 구성
        - 한 익스텐트는 하나의 테이블이 독점
            - 한 익스텐트에 담긴 블록은 모두 같은 테이블 블록
        - MS-SQL Server는 한 익스텐트를 여러 오브젝트가 같이 사용할 수도 있다.
        - 익스텐트끼리는 연속된 공간이 아니다.
        - Oracle에서 세그먼트에 할당된 익스텐트 목록을 조회하는 방법
            ```SQL
                select 
                    segment_type, tablespace_name, extent_id, block_id, blocks
                from
                    dba_extents
                where
                    owner = USER
                    and
                    segment_name = 'MY_SEGMENT'
                order by
                    extent_id;
            ```
    - 데이터 블록
        - 사용자가 입력한 레코드를 실제로 저장하는 공간
        - DB2, SQL Server는 블록 대신 페이지(page)라는 용어 사용
        - 한 블록은 하나의 테이블이 독점
            - 한 블록에 저장된 레코드는 모두 같은 테이블 레코드
            - 블록 : 데이터를 읽고 쓰는 단위
        - DBA(Data Block Address)
            - 모든 데이터 블록은 디스크 상에서 몇 번 데이터 파일의 몇 번째 블록인지를 나타내는 자신만의 고유 주소값을 가진다.
            - 인덱스를 이용해 테이블 레코드를 읽을 때는 인덱스 ROWID를 이용한다.
                - LOWID = DBA + 로우 번호(블록 내 순번)
            - 테이블을 스캔할 때는 테이블 세그먼트 헤더에 저장된 익스텐트 맵을 이용한다.
                - 익스텐트 맵을 통해 각 익스텐트의 첫 번째 블록 DBA를 알 수 있다.
                - 익스텐트는 연속된 블록 집합이므로 테이블을 스캔할 때는 첫 번째 블록 뒤에 연속해서 저장된 블록을 읽으면 된다.
## 1.3.3 블록 단위 I/O
- 오라클은 기본적으로 8KB 크기의 블록을 사용하며 2KB, 4KB, 16KB 크기 블록을 사용할 수도 있다.
    - 블록 사이즈를 확인하는 방법
        ```SQL
            show parameter block_size
        ```
    - v$parameter 뷰 조회하는 방법
        ```SQL
            select value from v$parameter where name = 'db_block_size';
        ```
- MS SQL Server는 8KB 단일 사이즈 블록(=페이지)만 지원한다.
- 테이블뿐만 아니라 인덱스도 블록 단위로 데이터를 읽고 쓴다.
## 1.3.4 시퀀셜 액세스 vs 랜덤 액세스
- 테이블 또는 인덱스 블록을 액세스(=읽는) 방식으로는 시퀀셜 액세스와 랜덤 액세스가 있다.
    - 시퀀셜 액세스
        - 논리적 또는 물리적으로 연결된 순서에 따라 차례대로 블록을 읽는 방식
        - 인덱스 리프(Leaf) 블록은 서로 앞뒤 리프 블록을 가리키는 포인터를 가지고 있어 키 값 순서대로 논리적 시퀀셜 액세스가 가능
            - 인덱스 키와 테이블 ROWID를 담고 있음
        - 테이블 블록은 서로 논리적 연결고리를 가지고 있지 않다.
            - 세그먼트에 할당된 익스텐트 목록을 세그먼트 헤더에 맵으로 관리한다.
            - 익스텐트 맵은 각 익스텐트의 첫 번째 블록 주소 값을 가진다.
            - 읽어야 할 익스텐트 목록을 익스텐트 맵에서 얻고, 각 익스텐트의 첫 번째 블록 뒤에 연속해서 저장된 블록을 순서대로 읽는다. (Full Table Scan)
    - 랜덤 액세스
        - 논리적, 물리적 순서를 따르지 않고, 레코드 하나를 읽기 위해 한 블록씩 접근하는 방식
## 1.3.5 논리적 I/O vs 물리적 I/O
### 물리적 버퍼캐시
- SGA 구성요소 
- 데이터 캐시
    - 디스크에서 읽은 데이터 블록을 캐싱해둬서 같은 블록에 대한 반복적 I/O Call을 줄임
    - 오라클에서 버퍼캐시 사이즈 확인하는 방법
        ```SQL
            show sga
        ```
### 논리적 I/O
- SQL을 처리하는 과정에 발생한 총 블록 I/O
- 메모리상의 버퍼 캐시를 경유하는 메모리 I/O + 메모리를 경유하지 않는 Direct Path I/O
    - 메모리 I/O는 전기적 신호

### 물리적 I/O
- 디스크에서 발생한 총 블록 I/O
- SQL 처리 도중 읽어야 할 블록을 버퍼캐시에서 찾지 못할 때만 디스크를 액세스
    - 논리적 블록 I/O 중 일부를 물리적으로 I/O 한다.
    - 액세스 암을 통해 물리적 작용이 일어나서 메모리 I/O보다 10,000배쯤 느리다.
        - 디스크 경합이 심하면 더 느리다.
- 데이터 입력이나 삭제가 없어도 물리적 I/O는 SQL을 실행할 때마다 다르다.
    - SQL을 연속으로 실행하면 DB 버퍼캐시에서 해당 테이블 블록 점유율이 높아져서 물리적 I/O가 줄어든다.
    - 한참 후 다시 실행하면 DB 버퍼캐시가 다른 테이블 블록으로 채워져서 물리적 I/O가 늘어난다.
### 버퍼캐시 히트율
- Buffer Cache Hit Ratio, BCHR
    - (캐시에서 곧바로 찾은 블록 수 / 총 읽은 블록 수) * 100
    - ( (논리적 I/O - 물리적 I/O) / 논리적 I/O) * 100
    - ( 1 - (물리적 I/O / 논리적 I/O) ) * 100
- 온라인 트랜잭션을 주로 처리하는 애플리케이션이라면 시스템 레벨에서 평균 99% 히트율을 달성해야 한다.
- 실제 SQL 성능을 향상하려면 물리적 I/O가 아닌 논리적 I/O를 줄여야 한다.
    - 물리적 I/O = 논리적 I/O * (100% - BCHR)        
    - 논리적 I/O는 일정하므로 물리적 I/O는 BCHR에 의해 결정된다.
    - BCHR은 시스템 상황에 따라 달라진다.
    - 물리적 I/O는 시스템 상황에 의해 결정되는 통제 불가능한 외생변수이다.
        - 메모리를 증설해서 DB 버퍼캐시 크기를 늘리는 방법 외에는 직접 줄일 방법이 없다.
    - 논리적 I/O는 SQL을 튜닝해서 총 블록 개수를 줄이면 되고 통제 가능한 내생변수이다.
    - 논리적 I/O를 줄임으로써 물리적 I/O를 줄이는 것이 곧 SQL 튜닝이다.
## 1.3.6 Single Block I/O vs Multiblock I/O
### Single Block I/O
- 한 번에 한 블록씩 요청해서 메모리에 적재하는 방식
- 인덱스를 이용할 때는 기본적으로 인덱스와 테이블 블록 모두 Single Block I/O 방식을 사용한다.
- 인덱스는 소량의 데이터를 읽을 때 주로 사용한다.
### Multiblock I/O
- 한 번에 여러 블록씩 요청해서 메모리에 적재하는 방식
- 많은 데이터 블록을 읽을 때 효율적
    - 테이블 전체를 스캔할 때
- 테이블이 클수록 Multiblock I/O 단위도 크면 프로세스 잠자는 횟수를 줄여줘서 효율적이다.
- 캐시에서 찾지 못한 특정 블록을 읽으려고 I/O Call 할 때 디스크 상에 그 블록과 `인접한` 블록들을 한꺼번에 읽어 캐시에 미리 적재하는 기능
    - 인접한 블록 : 같은 익스텐트에 속한 블록
    - Multiblock I/O 방식으로 읽어도 익스텐트 경계를 넘지 못한다.
- DBMS 블록 사이즈가 얼마건 OS 단에서는 보통 1MB 단위로 I/O를 수행
    - OS마다 다름
- Multiblock I/O 단위 확인 방법
    ```SQL
        show parameter db_file_multiblock_read_count
    ```
- Multiblock I/O 단위 수정 방법
    ```SQL
        alter session set db_file_multiblock_read_count = 128;
    ```
    - 오라클 레벨 I/O 단위가 8KB이므로 db_file_multiblock_read_count 파라미터 128이 최대이다.
        - 8KB * 128 = 1MB
## 1.3.7 Table Full Scan vs Index Range Scan
### Table Full Scan
- 테이블 전체를 스캔해서 읽는 방식
- 시퀀셜 액세스와 Multiblock I/O 방식으로 디스크 블록을 읽는다.
- 한 블록에 속한 모든 레코드를 한 번에 읽어 들이고, 캐시에서 못 찾으면 `한 번의 수면(I/O Call)을 통해 인접한 수십~수백 개 블록을 한꺼번에 I/O하는 매커니즘`
- 스토리지 스캔 성능이 좋아지는 만큼 성능도 좋아진다.
### Index Range Scan
- 인덱스를 이용해서 읽는 방식
- 큰 테이블에서 소량 데이터를 검색할 때 이용
- 랜덤 액세스와 Single Block I/O 방식으로 디스크 블록을 읽는다.
- 캐시에서 블록을 못 찾으면 `레코드 하나를 읽기 위해 매번 잠을 자는 I/O 매커니즘`
    - 많은 데이터를 읽을 때는 불리
- 읽었던 블록을 반복해서 읽는 비효율이 있다.
    - 많은 데이터를 읽을 때 물리적인 블록 I/O 뿐 아니라 논리적인 블록 I/O 측면에서도 불리
## 1.3.8 캐시 탐색 메커니즘
- 버피 캐시 탐색 과정을 거치는 오퍼레이션
    - 인덱스 루트 블록을 읽을 때
    - 인덱스 루트 블록에서 얻은 주소 정보로 브랜치 블록을 읽을 때
    - 인덱스 브랜치 블록에서 얻은 주소 정보로 리프 블록을 읽을 때
    - 인덱스 리프 블록에서 얻은 주소 정보로 테이블 블록을 읽을 때
    - 테이블 블록을 Full Scan할 때
- DBMS는 버퍼캐시를 해시 구조로 관리한다.
    - 해시 알고리즘으로 버퍼 헤더를 찾고 거기서 얻은 포인터로 버퍼 블록을 액세스한다.
    - 같은 입력 값은 항상 동일한 해시 체인(=버킷)에 연결된다.
    - 다른 입력 값이 동일한 해시 체인에 연결될 수 있다.
    - 해시 체인 내에서는 정렬이 보장되지 않는다.
### 메모리 공유자원에 대한 액세스 직렬화
- 버퍼캐시는 SGA 구성요소이다.
    - 버퍼캐시에 캐싱된 버퍼블록은 모두 공유자원이다.
        - 공유자원은 모두에게 권한이 있어 누구나 접근할 수 있다.
            - 하나의 버퍼 블록을 두 개 이상의 프로세스가 동시에 접근할 때 블록 정합성에 문제가 발생한다.
        - 자원을 공유하는 것처럼 보여도 내부에선 한 프로세스씩 순차적으로 접근하도록 구현하는 직렬화 메커니즘(=줄 세우기)이 필요하다.
            - 줄서기가 가능하도록 지원하는 메커니즘이 래치(Latch)이다.
                - 자물쇠를 열 수 있는 키를 획득한 프로세스만 체인으로 진입할 수 있다.
- SGA를 구성하는 서브 캐시마다 별도의 래치가 존재한다.
- 버퍼캐시에는 캐시버퍼 체인 래치, 캐시버퍼 LRU 체인 래치 등이 작동한다.
- 캐시버퍼 체인뿐만 아니라 버퍼블록 자체에도 직렬화 메커니즘이 존재한다.
    - 버퍼 Lock
        - 오라클에서 래치를 해제한 상태로 버퍼블록 데이터를 읽고 쓰는 도중에 후행 프로세스가 같은 블록에 접근해서 데이터를 읽고 써서 데이터 정합성에 문제가 생기지 않도록 방지하기 위해 사용
        - 캐시버퍼 체인 래치를 해제하기 전에 버퍼 헤더에 Lock을 설정
